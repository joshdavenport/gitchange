Only mutating commands contend — reads take no lock (`repo.rs`). The lock primitive stays fail-fast and a lock is never taken from a live holder (ADR 0002, amended: frontends may retry briefly, as the engine already does; no writer queues). On contention the CLI retries with short sleeps for a bounded budget — shape, not constant: roughly a couple of seconds — so a live TUI's brief hold never surfaces. The writer records its PID in the lockfile at take (core work, not built), and PID recycling fails safe: a stale lock can look held, a dead PID genuinely means no holder. Budget exhausted with the holder alive or the PID unreadable (assume-alive is the safe direction): exit `3`, the transient class — retry the same command unchanged; the text never advises removal. Exhausted with the PID dead: an ordinary exit `1` refusal naming the accurate resolution — remove `<path>` and retry. The CLI never auto-breaks a lock (check-then-steal race; `state_file.rs`'s never-silently-stolen invariant stands). No flags: retry is neither a guard nor an override, so ADR 0015 maps nothing, and a `--lock-timeout` knob would tune around persistent contention instead of surfacing it. Today's built text ("remove the lockfile and retry") is a standing hazard this cures.
