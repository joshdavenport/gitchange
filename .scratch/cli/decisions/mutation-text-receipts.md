No mutating command takes `--json`. The receipt is text: the op's echo, one line on stdout; each advisory a `gitchange: notice: <message>` line on stderr, every severity alike — stderr is messaging, not warning, and severity stays the presentation layer's (CONTEXT.md, **Advisory**). The reads own the machine surface: a receipt is a tripwire, not a data carrier — the records keep the facts, and `status --json`/`diff --json` re-read them. This is the VCS lineage's stated contract (gh: "keep `--json` support scoped to only list- and view-type commands"; git porcelain and jj expect mutate-then-re-read), and no surveyed tool puts warnings inside a stdout mutation envelope. The echo names the handle where the op mints one (commit's echo carries the new commit) and counts soft-fail skips — `staged 3 of 5 hunks (2 skipped as stale)` — so stdout alone trips the re-read even when a harness drops stderr; echoes are composed in core (ADR 0006/0007 — core work, not built). Exit `1` leaves stdout empty: a failed command produces no result; the refusal and any per-hunk notices are stderr's. Neither echo nor notice text is a parsing contract — agents act on exit codes and re-read for facts — but `Advisory::message` stays the one canonical string (ADR 0006), so rewording is deliberate, never free. Reversibility settled the polarity: under the additive contract a future `--json` receipt is a non-breaking addition, while an envelope shipped now becomes API on day one.
