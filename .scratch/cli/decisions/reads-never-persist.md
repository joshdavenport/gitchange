Every read-only CLI invocation — `status`, `diff`, the bare `changelist` listing, with or without `--json` — runs a read-only refresh: the full recompute, no writes. No capture, no record updates, no baseline stamp. Ownership reports what the records say: record-derived ownership (tier-2 inheritance, dormant revival) shows on reads; context-derived ownership (capture, entry-unit join — anything needing the active marker) never previews, so a recordless hunk is `unassigned`. Decisions happen only in persisting refreshes — the engine's, and the one inside each mutating op — and each decision's advisories ride that refresh's output, once, to the actor who triggered it. There is no advisory journal and no `advisories` command: read envelopes carry no advisories field — not because the recompute produces none (`DormantRevival`, `AmbiguousOverlap`, and `HeadMoveDormancy` fire regardless of capture; only `StaleHunk` is op-only) but because the read path discards them: a read commits no decision, so its advisories are previews the next persisting refresh re-makes and delivers once, on its receipt — surfacing them on reads would double-deliver and repeat on every read. The filter is core's, structural: the read-only refresh's return type carries no advisories, so no frontend can leak them (core work, not built). A discarded receipt loses the narrative while the records keep the facts, and a retrospective surface would need per-reader cursors (reader identity) or recreate the consumed-by-first-reader hazard. Deferred capture is the accepted cost: with no TUI running, a new hunk stays unassigned until the next mutation persists, so that mutation's receipt can advise decisions unrelated to its target. A mutation validates against its internal refresh's snapshot, so a capture made by that refresh feeds the op's own scope — `switch fix-login` → edit → `add fix-login` stages the just-captured hunks: the solo git-habit flow works unchanged.
